College Football Game Data Ingress

Revised proposal · September 30, 2026 · Free APIs and on-demand refresh

Selected direction: Use free CFBD access for games and results, and free The Odds API access for current spreads and prices. The Games page refreshes the current Monday–Sunday window only when the user clicks Refresh.

Prioritize upcoming FBS games and keep completed games visible through Sunday for reviewing results. No scheduled ingestion or automatic page-load refresh. No paid subscriptions or historical-odds purchase.

This subsequent document refines the MVP design to FBS coverage and on-demand ingress. All other MVP requirements remain, including the canonical domain, dry-run execution, immutable bets, and eventual settlement. CHIP has accepted the defaults below. This document is the implementation direction; implementation progress is tracked in the sibling backend and front_end plans.

2. What “current week” means

  • Accepted timezone: America/Los_Angeles. Use one configured application timezone for both the displayed window and weekly limiter, regardless of browser timezone.
  • The window begins Monday at 00:00 and ends immediately before the following Monday at 00:00 in that timezone. Convert those calendar boundaries to UTC for provider queries and storage; handle daylight-saving changes using timezone rules, not a fixed 168-hour interval.
  • Example: Wednesday September 30, 2026 shows September 28–October 4. Refresh on Sunday October 4 still retrieves that week’s schedule/results. On Monday October 5, the current window changes to October 5–11.
  • The application calendar window is separate from CFBD’s football season/week numbering. Preserve provider season/week and season type; never infer a football week number from the Monday date.
  • Accepted FBS scope: Both participating teams must be classified FBS for the relevant season. Exclude FBS-versus-FCS games. Verify both teams rather than assuming a provider’s FBS filter guarantees this.
  • Include scheduled, running, completed, and canceled games in the window. Only upcoming games offer new spread selections. Sunday refresh updates final scores when CFBD has published them; it does not guarantee immediate provider finalization.
  • Window membership follows the latest confirmed kickoff. Retain stored games and bet history when a game moves out of the window. An unknown kickoff is held for review rather than assigned a fictional time.

After Monday rollover, previously imported games and results remain stored and accessible through game/run history. No automatic catch-up occurs for an unrefreshed prior week; refreshing prior weeks is outside this initial current-week flow.

  1. Opening the page reads PostgreSQL only. Show an empty-state prompt to refresh when no current-week games are stored.
  2. Refresh is an explicit backend write operation; the frontend never calls providers directly. The server calculates the current window and enforces limits across all tabs/users sharing the provider keys.
  3. Resolve overlapping football weeks from CFBD’s season calendar, then request explicit schedule windows by year, seasonType, and week. Filter returned games to the exact Pacific Monday–Sunday kickoff range and require both teams FBS. Cache calendars by season; refresh calendar metadata only within a user-triggered refresh when needed. Count every metadata and schedule request against the provider budget. Preserve provider status and final scores; do not infer completion from the clock.
  4. Request The Odds API NCAAF spreads for the window using one US region and decimal odds. Filter locally to mapped FBS games and upcoming kickoffs. Skip the odds call if no eligible upcoming games remain, so Sunday results-only refresh does not spend odds credits unnecessarily.
  5. Validate and commit each provider stage independently. If games succeed but odds fail, retain updated games and the prior odds observation, and clearly report the partial result. Never report “all refreshed” for a partial run.
  6. Return a bounded synchronous response for this small slice. Record the run before requesting data. A tab closing or response timing out must not allow a duplicate concurrent run; recover the recorded run server-side on the next request. No worker queue or scheduled job is required.

Planned API addition: POST /api/games/refresh with no caller-selected week. Use GET /api/games?window=current for stored current-week games; preserve unfiltered GET behavior for existing callers. No separate refresh-status endpoint or status dashboard is required.

4. Weekly application limits and provider limits

Our weekly limit controls button usage. Provider allowances are monthly and do not reset just because our calendar week changes. Both must pass before spending API credits.

ControlAccepted default / behavior
Application weekly budget20 external refresh attempts per Monday–Sunday window, shared across the deployment. An accepted refresh that starts provider work consumes one attempt even if a provider later fails. Requests blocked before any external call do not consume an attempt.
Click protectionOne active refresh at a time and a 60-second cooldown between accepted attempts. Disabled UI plus transactional server enforcement; browser disabling alone is insufficient.
Sunday result accessReserve 2 of the 20 attempts for Sunday. Before Sunday, stop after 18. Sunday can use any remaining attempts. Explain the Sunday reservation in the popup when it blocks a refresh.
Provider budgetsTrack each provider separately, conservatively reserving estimated cost before each call. For Odds API read actual remaining/used/last-cost headers; for CFBD use exposed quota metadata where available plus a local call ledger. External use of shared keys can exhaust quotas earlier.
Monthly reserveAccepted 10% safety reserve: target at most 450 Odds API credits and 900 CFBD calls per provider billing period. Reserve is a safety margin, not a guarantee of Sunday access if the provider allowance is exhausted.
Provider reset / temporary throttlingPersist known reset times and Retry-After when supplied. If reset timing is not known, say so; never invent a date. A temporary provider rate limit differs from monthly credit exhaustion.

With at most 20 attempts per week, a calendar month touches at most six application weeks: at most 120 attempts within that month. With one region and one market, a normal odds call costs one credit. The estimate leaves room below the free 500-credit allowance; CFBD batch counts, extra metadata calls, and uncertain request outcomes still need measurement. No automatic retries in the first version: show the failure and allow another deliberate click after cooldown, charging/reserving it separately.

Use durable PostgreSQL counters/reservations so restarts, concurrent requests, and HTTP timeouts cannot reset or overspend the budget. Unknown provider-call outcomes remain conservatively charged. Weekly reset creates a new week bucket lazily on access; no midnight job is needed. Monthly accounting follows each provider’s own quota period, not the weekly application clock.

Informative messages

  • Weekly limit: “You’ve used all 20 refreshes for September 28–October 4. Refresh is available again Monday October 5 at 12:00 AM Pacific. Saved data remains available.”
  • Sunday reserve: “You’ve used 18 refreshes. Your remaining 2 refreshes are available Sunday so you can update this week’s results.”
  • Provider quota: “The Odds API free allowance is exhausted. Games/results were updated from CFBD; spreads remain from the last successful refresh. Provider reset: [known time, or ‘not yet known’].”
  • Cooldown: “Refreshed recently. Try again in 42 seconds.”
  • Partial refresh: “Games updated; odds could not be refreshed. Last odds update: [time].”

Include a machine-readable reason, retry availability, per-provider outcome, and last-success times. Limit failures retain readable stored data. Missing credentials and authentication failures receive a configuration message rather than misleading quota wording. A provider budget exhausted for one stage need not block the other stage if it can still update data.

5. Automatically choose a free-access bookmaker

A bookmaker is the sportsbook whose spread and price appears in the feed. The free API can include several; no separate bookmaker subscription is required for this dry-run simulator. CHIP does not need to choose one.

Accepted automatic rule: For each game, keep its previously selected bookmaker if it still supplies a valid paired spread in the current free-key response. Otherwise choose the available valid bookmaker with the lexicographically smallest stable provider key. This is deterministic rather than dependent on response ordering. Record the bookmaker with each observation, including when it changes.

  • Select both teams’ prices and opposite handicap lines from the same full-game bookmaker market and observation. Never mix books or manufacture a missing price.
  • There is no “best price” shopping or averaging across books. If none has a valid pair, show “Spread unavailable” while retaining the game.
  • Use a single US region and one spread market to bound request cost. Choose only bookmakers present in the free-key response; no fixed bookmaker entitlement is assumed.

The official API documentation defines odds parameters, bookmaker identity, outcome points/prices, and usage headers.

6. Stored snapshots, identity, and results

  • Keep canonical UUIDs and provider-event mappings outside the domain. CFBD owns canonical teams, season/week, kickoff, and results. Match Odds API events using explicit team aliases, participants, and kickoff proximity; require a unique match. Unknown or conflicting matches are flagged rather than guessed. Follow established provider IDs through rescheduling.
  • Validate required fields and source statuses. Store neutral-site/season-type/provider-state metadata. Quarantine unknown kickoff/week/status values that cannot fit the current schema; a future schema extension must be explicit.
  • Parse price and line using Decimal and preserve current schema precision: line two decimal places, decimal price four, with documented rounding. Require finite prices greater than one and exactly two matching teams with opposite lines, including zero.
  • Persist current Game → Market → Selection projections and an auditable quote observation containing bookmaker, source timestamp if supplied, and fetch time. Commit paired selections atomically; reject older observations overwriting newer ones. A successful scoped response lacking a usable quote removes current availability without deleting prior observations.
  • On-demand snapshot policy: Remove the previously proposed 30-minute expiry. Stored valid pregame quotes remain usable for theoretical simulation until kickoff or explicit invalidation. Keep fetch time and bookmaker in stored quote provenance; these are saved observations, not a promise of a live executable price. Refresh failure preserves the prior quote and displays the failure.
  • At kickoff, selections become unavailable for new bets based on current server time even without a refresh. A game can remain “scheduled” in stored source state until the next refresh; the UI must not imply that this stale status means it is still upcoming.
  • Bet creation later rechecks known kickoff, game/market/selection eligibility and snapshots line, price, stake, and quote provenance. Existing bets never change when refreshed selections change.
  • Completion requires explicit final confirmation and both scores, not elapsed time alone. Score corrections are audited. Later settlement design determines how to correct settled outcomes; canceled/postponed games block new decisions.

Preserve run outcomes, quota ledgers, identity maps, normalized observations, and result-change audit records. Raw full-response retention is not required in this MVP proposal; choose it separately if necessary for debugging. Existing demo data stays clearly labeled and is never matched onto real provider games.

7. Simple Games-page Refresh button

Add one Refresh button to the Games page. Disable it while its request is in flight. On completion, show one popup and reload the stored current-week games if any data changed. No quota panel, status dashboard, separate status request, or additional refresh controls.

  • Success: “Refresh successful. 17 refreshes remaining this week.” Count includes any Sunday-reserved attempts; if relevant append “2 are reserved until Sunday.”
  • Failure: “Refresh failed: [useful reason]. [Remaining refreshes and retry timing when known].” Include cooldown, weekly/Sunday restriction, exhausted provider allowance, configuration failure, timeout, or partial update details.
  • Partial failure: “Refresh failed to update odds; games/results were updated. Saved odds were kept. 17 refreshes remaining this week.” Do not erase successful changes or show full success.
  • Empty week: A successful refresh with no FBS games is success, with “No FBS games this week.” Do not query odds when there are no eligible upcoming games.

Keep the existing Games page simple. The backend filters the current window, preserves saved quote provenance, and enforces kickoff eligibility. A price is the saved provider observation rather than a live-price guarantee. Completed games show scores; run settlement and P&L remain separate MVP work.

Backend response contract

The refresh response uses a single envelope: success (boolean), reason (stable code), message (safe popup text), remaining_refreshes (integer or null if database state is unavailable), reserved_for_sunday, retry_at (UTC timestamp or null), data_changed, and run_id (UUID or null). Backend audit records retain stage counts and outcomes without putting implementation details in the popup.

HTTP 200 for a finished run (success true for full success, false for partial/failure); 429 for weekly/cooldown/provider-budget rejection before work; 409 for an already active refresh; 503 for database unavailability; 422 for invalid query/body input. All handled refresh errors use the envelope. A transport error without an envelope shows a generic failure popup. A rate-limit result reports remaining attempts even if reserved; provider monthly reset and application weekly retry are distinct.
