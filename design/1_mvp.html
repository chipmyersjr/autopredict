College Football Betting Simulator

MVP Design Proposal & Agentic Development Plan
Purpose: Build a small, complete vertical slice first: college football games and spreads → random strategy → theoretical bets → settlement → profit/loss.

1. Product Vision

MVP — College Football Betting Simulator

A web-based platform that lets a User run betting strategies against college-football spread markets using a Dry Run adapter.

  • Games: View upcoming college football games and their current spreads.
  • Markets: Represent different types of bets in a flexible way, starting with spread.
  • Strategies: Start with one baseline strategy: Random Strategy, which randomly selects available bets.
  • Runs: A User starts a Run against a set of games using a selected Strategy.
  • Dry Run: Records theoretical bets, settles them when games finish, and calculates bankroll, profit/loss, ROI, and other results.
  • Admin Dashboard: Manage games, strategies, runs, and bets; view spreads, active runs, bet history, and performance visualizations.
MVP Goal: Games → Spreads → Strategy → Bets → Results → P&L

Future State — AI Strategy & Experimentation Platform

The simulator evolves into an AI-native platform for developing, evaluating, and continuously improving betting strategies.

Data → Prediction → Strategy → Bets → Results → Evaluation → Learning
  • More markets and sports: totals, moneylines, player props, NFL, NBA, etc.
  • Advanced strategies: statistical models → ML → LLM-powered strategies → reinforcement learning.
  • Richer real-time and historical data.
  • Strategy experimentation, backtesting, comparison, and versioning.
  • AI agents that analyze markets, develop strategies, run experiments, and propose improvements.
  • Reinforcement learning with a defined reward function, using Random Strategy as the baseline to beat.
  • Eventually, coding agents can modify the system/strategies, run evaluations, and receive rewards based on measurable improvement.
  • A future Kalshi execution adapter can be added without making Kalshi part of the MVP domain model.
  • Advanced analytics: probability calibration, expected value, drawdown, risk, strategy comparisons, model performance, and experiment history.

In Scope

  • College football
  • Games

  • Spread selections
  • One Random Strategy
  • Runs
  • Bets
  • Dry-run execution
  • Game-result settlement
  • Theoretical bankroll and P&L
  • Admin dashboard

Explicitly Out of Scope

  • Kalshi integration or real-money execution
  • ML, LLMs, or reinforcement learning

  • Other sports or market types
  • Kafka, Redis, Kubernetes, or distributed infrastructure unless later justified
  • Multi-tenant SaaS concepts; the domain uses User

3. Initial Domain Model

The MVP uses a simple canonical domain model. External provider-specific identifiers should not leak into the domain prematurely.

EntityPurposeInitial fields / concepts
UserOwner of simulations and strategies.id, name, email, created_at
GameActual college football game.id, season, week, home_team, away_team, start_time, status, home_score, away_score
MarketSomething that can be bet on for a game.id, game_id, type, status
SelectionConcrete choice within a market.id, market_id, side/name, line, price
StrategyLogic that generates betting decisions.id, user_id, name, type, configuration
RunExecution of a strategy against selected games.id, user_id, strategy_id, bankroll, stake_per_bet, status, metrics
BetImmutable record of a strategy decision.id, run_id, selection_id, stake, price, status, outcome, profit, timestamps

Market / Selection Design

A spread should not be a column directly on Market. The design should support future market types without prematurely implementing them.

Game
 └── Market (type = SPREAD)
      ├── Selection: USC -3.5
      └── Selection: UCLA +3.5

Future examples could include TOTAL, MONEYLINE, or PLAYER_PROP, but these are not implemented in the MVP.

4. Data Requirements

The simulator needs two categories of information:

  1. Game information: teams, game time, season/week, status, and final scores.
  2. Market information: the spread currently available for each game.

For the MVP, external provider details belong in an ingestion/integration layer rather than the core domain.

External Data Provider
        ↓
   Ingestion Layer
        ↓
  Canonical Domain
        ↓
    PostgreSQL
        ↓
      FastAPI
        ↓
       React

The first implementation can use seeded/local data to prove the application path. A real college-football data provider can then replace the seed data without changing the UI/domain contract.

5. Dry Run Adapter

The strategy never places bets directly. It produces a BetDecision; the Dry Run adapter records the theoretical execution.

Strategy
   ↓
BetDecision
   ↓
DryRunAdapter
   ↓
Bet
   ↓
Game Result
   ↓
Settlement
   ↓
Profit / Loss
   ↓
Run Metrics

Bet Lifecycle

OPEN
  ↓
BET PLACED
  ↓
GAME COMPLETES
  ↓
WIN / LOSS
  ↓
SETTLED

The bet captures the spread/price/stake available at decision time. If market data later changes, the historical bet is not rewritten.

Settlement

Settlement is based on the final game score and the spread associated with the selection.

Example:

USC 31
UCLA 24

USC -3.5

Score margin = 7
7 > 3.5
→ WIN

The exact accounting model will be finalized with the initial data contract. The key requirement is deterministic tracking of theoretical bankroll, stake, outcome, and realized profit/loss.

8. Admin Dashboard

The admin dashboard is explicitly part of the MVP.

  • Dashboard: bankroll, active runs, recent results, and performance.
  • Games: upcoming games, start times, teams, and available spreads.
  • Strategies: manage the Random Strategy.
  • Runs: create and inspect strategy runs.
  • Bets: view bets, selections, outcomes, and P&L.

9. Vertical Slice Development Plan

Vertical Slice #1 — Games & Spreads

Open the UI and see realistic college football games and their spreads. Build the database models, FastAPI endpoints, React Games page, and initial seed/data ingestion mechanism.

Vertical Slice #2 — Random Strategy

Select games and execute the Random Strategy. The strategy receives available spread selections and produces betting decisions.

Vertical Slice #3 — Dry Run Bets

Record theoretical bets and show them in the UI. Introduce the Dry Run adapter and connect decisions to Bets and Runs.

Vertical Slice #4 — Settlement & P&L

Settle open bets when games complete and calculate bankroll, profit/loss, ROI, and run-level metrics.

MVP is complete when:
A User can open the dashboard → see college football games and spreads → start a Random Strategy Run → see theoretical bets → settle completed games → see the resulting P&L.

10. Agentic Development Approach

The coding agent should not be asked to build the entire future platform in one pass.

Requirement
    ↓
Coding Agent
    ↓
Implementation
    ↓
Automated Tests
    ↓
Run Application
    ↓
Evaluate Acceptance Criteria
    ↓
Human / Agent Review
    ↓
Next Slice

The future AI/RL system will use the same philosophy at a larger scale: changes are evaluated against objective metrics rather than accepted simply because the code looks good.

11. MVP Success Criteria

  • The application runs locally with documented setup steps.
  • A browser UI displays college football games and spread selections.
  • Games and markets are persisted in PostgreSQL.
  • The Random Strategy can be executed against selected games.
  • The Dry Run adapter records bets without placing real wagers.
  • Completed games can settle open bets deterministically.
  • Runs expose starting bankroll, ending bankroll, bets, wins/losses, profit, and ROI.
  • The UI makes the complete Games → Spreads → Strategy → Bets → Results → P&L loop visible.
  • The Strategy/Execution boundary remains clean enough to support future ML, AI, RL, and real-market adapters.
Guiding principle: Build the smallest complete system first. Avoid speculative infrastructure and future-provider abstractions until the product actually needs them.
